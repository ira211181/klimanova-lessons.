01 · Мета й маршрут уроку

Після заняття ви зможете розпізнати первинні та зовнішні ключі, визначати типи зв’язків, будувати просту реляційну модель і перевіряти посилальну цілісність.

Знаю

PK, FK, 1:1, 1:N, N:M, проміжна таблиця.

Умію

Створюю схему, перевіряю ключі, знаходжу залежні записи.

Дотримуюся

Правил безпеки, захисту персональних даних і доброчесності.

Безпека: працюйте з вигаданими навчальними даними, не публікуйте особисті відомості, робіть перерви та бережіть зір.

02 · Ключі та зв’язки

🔑 Первинний ключ (PK)

Поле або набір полів, що однозначно визначає кожний запис таблиці. Значення PK не повторюються й не можуть бути NULL.

Приклад: student_id у таблиці «Учні».

🔗 Зовнішній ключ (FK)

Поле або набір полів, що посилається на ключ у пов’язаній таблиці. Забезпечує посилальну цілісність за налаштованого обмеження.

Приклад: student_id у таблиці «Участь».

Три типи зв’язків

1:1 · один до одного

Один працівник — одна активна перепустка (за правилом системи).

1:N · один до багатьох

Один клас — багато учнів. FK зазвичай з боку «багато».

N:M · багато до багатьох

Учні — гуртки. Реалізується через проміжну таблицю «Участь».

Запам’ятайте: для N:M у реляційній моделі використовують дві залежності 1:N через проміжну таблицю. Для пари FK доцільно забезпечити унікальність, якщо повторна участь не передбачена.

Приклад SQL (для ознайомлення)

CREATE TABLE Students (
  student_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);
CREATE TABLE Clubs (
  club_id INTEGER PRIMARY KEY,
  title TEXT NOT NULL
);
CREATE TABLE Membership (
  student_id INTEGER NOT NULL,
  club_id INTEGER NOT NULL,
  PRIMARY KEY (student_id, club_id),
  FOREIGN KEY (student_id) REFERENCES Students(student_id),
  FOREIGN KEY (club_id) REFERENCES Clubs(club_id)
);
Типові помилки: використовувати ім’я як унікальний PK; записати в FK неіснуючий ID; дублювати пару учень–гурток; вважати N:M звичайним 1:N. Зверніть увагу: конкретна СКБД може вимагати окремого увімкнення перевірки зовнішніх ключів.

05 · Практична робота «Шкільні гуртки без повторів»

Мета — спроєктувати реляційну модель, яка зберігає участь учнів у гуртках без зайвого дублювання. Орієнтовно 20–25 хвилин.

  1. Відкрийте табличний редактор або СКБД і створіть три таблиці: «Учні», «Гуртки», «Участь».
  2. У таблиці «Учні» створіть student_id (унікальний PK), ім’я; у «Гуртки» — club_id (унікальний PK), назву.
  3. У таблиці «Участь» створіть student_id та club_id як зовнішні ключі, що посилаються на відповідні таблиці.
  4. Додайте навчальні записи: учні 101 — Марта, 102 — Денис, 103 — Олена; гуртки 11 — Робототехніка, 12 — Дизайн.
  5. Заповніть «Участь» парами (101,11), (101,12), (102,11), (103,12). Забезпечте унікальність пари.
  6. Побудуйте схему: «Учні» 1:N «Участь» N:1 «Гуртки». Поясніть, чому загалом це N:M.
  7. Спробуйте додати пару (999,11). Опишіть, чому коректна БД з перевіркою FK відхилить її.
  8. Отримайте список гуртків Марти, зробіть знімок схеми й напишіть висновок про посилальну цілісність.
Результат: три таблиці, схема зв’язків, приклад перевірки FK і короткий висновок. Оцінювання (12 балів): структура 3, ключі 3, зв’язки 3, перевірка й висновок 3.
